# Daily Lumos 系統機制

> 本文件說明系統各項功能「實際上是怎麼運作的」，
> 包含背後的判斷規則。寫給想了解運作細節的人看。

---

## 一、登入機制

- 使用者用 **Google 帳號**登入（透過 Firebase Authentication）。
- 第一次登入時，系統會在資料庫建立一筆個人資料，記下名稱、Email、頭像。
- 登入狀態由 Firebase 自動記住，下次開啟 App 不需重新登入。
- 開發測試環境另有「跳過登入」機制，僅供本地測試，不影響正式環境。

---

## 二、每日抽卡機制

### 一天只能抽一張

- 系統用「**今天的日期**」判斷使用者今天抽過了沒。
- 資料庫每位使用者有一個 `lastDrawDate`（最後抽卡日期）欄位。
- 抽卡後，`lastDrawDate` 更新成今天；當天再進來就顯示已抽的卡，不能再抽。

### 跨日自動重置

- 「今天」用**裝置的本地日期**計算（不是 UTC），避免跨時區誤判。
- 到了午夜，倒數計時歸零，抽卡功能自動解鎖，新的一天可以再抽。

### 經文怎麼來

1. 系統從**聖經全 66 卷書**中隨機選出一卷、一節。
2. 先向線上服務 `bible-api.com` 取得該節經文。
3. 若線上取不到（網路問題或服務異常），改用 App 內建的**本地備援經文**。
4. 因此「一定抽得到卡」，不會因為外部服務掛掉而卡住。

### 抽卡為什麼很快

- 抽卡後**先把卡片顯示在畫面上**，讓使用者立刻看到結果。
- 「寫入資料庫」這個動作放到**背景**進行，不擋住畫面。

---

## 三、AI 經文解析機制

- 抽到卡片後，可以**翻面**查看 AI 對這節經文的白話解析。
- 翻面時，前端呼叫後端函式 `api/analyze.ts`。
- 後端把經文內容包進提示詞，呼叫 **Claude AI**，取得解析文字。
- 解析結果會存進資料庫，下次看同一張卡不必重新產生。
- 另可開啟「整章閱讀」視窗，讀這節經文所在的**整章內容**，支援直書閱讀模式。

## 四、每日提醒推播機制（最複雜的部分）

### 整體流程

1. 使用者在「每日提醒設定」中開啟推播、設定提醒時間。
2. **外部排程器 cron-job.org 每分鐘**自動呼叫一次後端 `api/send-reminders.ts`。
3. 後端逐一檢查每位使用者，決定「現在這一刻」該不該推給他。
4. 對符合條件的人，透過 Firebase 推播通道送出通知。

> 為何用 cron-job.org：要讓提醒誤差控制在 1 分鐘內，排程器必須「每分鐘觸發、
> 且準時」。GitHub Actions 排程最小間隔 5 分鐘、整點常被延遲甚至丟棄，做不到，
> 故改用每分鐘精準觸發的 cron-job.org。

### 開啟推播時發生什麼

- 系統向使用者要求「通知授權」。
- 註冊一支背景小程式（Service Worker），它負責在 App 沒開時也能收通知。
- 取得這台裝置專屬的「推播識別碼」（FCM token），存進資料庫。

### 後端決定「該不該推」的判斷規則

後端撈出所有「**有開啟推播**」的使用者後，逐一套用以下檢查，
**任何一項不通過就跳過、不推播**：

| 檢查項目 | 規則 | 用意 |
|----------|------|------|
| 今天抽過卡了嗎 | 抽過 → 跳過 | 已經抽了就不打擾 |
| 今天通知過了嗎 | 通知過 → 跳過 | 同一天不重複轟炸 |
| 提醒時間到了嗎 | 還沒到 → 跳過 | 時間未到不提早推 |
| 是否超過補送視窗 | 超過 10 分鐘 → 跳過 | 避免推出過期的提醒 |
| 有沒有推播識別碼 | 沒有 → 跳過 | 沒識別碼無法送達 |

→ 全部通過，才會送出推播。

### 「補送視窗」是什麼

- 排程器每分鐘呼叫一次，正常情況提醒時間一到就推，誤差在 1 分鐘內。
- 補送視窗是**安全網**：萬一某幾次呼叫偶發失敗，規則允許在
  「**提醒時間到了之後的 10 分鐘內**」由後續呼叫補送。
- 例如設定 09:30，即使 09:30 那次呼叫失敗，09:31 的呼叫仍會補上。
- 但若超過 10 分鐘（已算過期提醒），就放棄不推。

### 推播時間可精確到「每分鐘」

- 使用者在設定畫面用「時 / 分」兩個選單組合提醒時間，可精確到任一分鐘
  （例如 08:00、08:17、21:45）。
- 排程器每分鐘觸發，足以準確命中任何分鐘設定。
- （早期版本曾限制為整點或半點共 48 個時段，那是 GitHub Actions 每 30 分鐘
  排程時代的限制；改用每分鐘排程後已開放到每分鐘。）

### 「先禱告再抽卡」的引導文案

- 推播文字共有 **6 則**，語氣溫暖、親切、口語、有帶領感。
- 每則都引導使用者「**先禱告、再抽卡**」，把今日箴言定位成主為你預備的禮物與方向。
- 每天依日期輪替一則：`索引 =（年＋月＋日的總和）÷ 6 的餘數`。
- 同一天所有人收到的是同一則。

六則完整文案如下（索引 0～5）：

| 索引 | 標題 | 內文 |
|------|------|------|
| 0 | 嘿，今天還沒和主說說話喔 | 先停下來，向主禱告一會兒，再抽今日箴言 — 領受這份為你預備的禮物。 |
| 1 | 主為你預備了今天的話 | 安靜下來，把心裡的事交給主，然後翻開卡片，看看祂給你的方向。 |
| 2 | 留三分鐘給自己，也給主 | 先禱告交託，再抽一張今日箴言 — 聽聽主今天想對你說什麼。 |
| 3 | 今天的箴言還在等你 | 別急，先和主禱告片刻，再來領受這句特別為你而寫的話。 |
| 4 | 新的一天，先深呼吸 | 把今天輕輕交給主禱告，然後抽一張卡，讓這份禮物陪你走下去。 |
| 5 | 主有話想對你說 | 先靜靜禱告，再翻開今日箴言 — 願這句話成為你今天的光與方向。 |

> 文案定義在 `api/send-reminders.ts` 的 `MESSAGES` 陣列；
> 修改文案時，請同步更新本表。

### 已送出後怎麼防止重複

- 成功送出後，把該使用者的 `lastNotifiedDate`（最後通知日期）標記成今天。
- 之後同一天的排程再跑，看到「今天通知過了」就會跳過。
- 若使用者的推播識別碼已失效，系統會自動清除它。

### 安全機制

- 排程器呼叫後端時需附帶一組密鑰（`CRON_SECRET`）。
- 後端會驗證這組密鑰，不符就拒絕，避免推播端點被外部任意呼叫。

## 五、「加到主畫面」教學機制

- 系統會自動**偵測使用者的作業系統**：iOS、Android、或電腦。
- 偵測方式：讀取瀏覽器資訊；iPad 會偽裝成 Mac，另用「觸控點數量」輔助判斷。
- **手機版**才會顯示「加到主畫面」教學，並依系統顯示對應的三步驟說明。
- **電腦版**不顯示教學、也不提供推播（推播主要為手機情境設計）。
- 系統也能判斷 App 目前是否已用「主畫面模式」開啟（即已安裝）。

## 六、資料儲存機制

所有資料存在 Firebase Firestore。主要結構：

```
users（使用者集合）
 └─ 每位使用者一筆文件
     ├─ 個人資料：名稱、Email、頭像
     ├─ lastDrawDate     最後抽卡日期
     ├─ lastNotifiedDate 最後推播通知日期
     ├─ pushEnabled      是否開啟推播
     ├─ pushHour / pushMinute  提醒時間（時、分）
     ├─ fcmToken         推播識別碼
     └─ cards（卡片子集合）
         └─ 每張抽過的卡一筆：經文、主題、AI 解析等
```

## 七、測試環境與正式環境的隔離

- 「發送測試通知」功能由環境變數 `ENABLE_PUSH_TEST` 控制。
- 正式環境不設這個變數，後端的測試端點會直接回傳 404（等於不存在）。
- 因此**測試功能絕不會出現在正式環境**，使用者看不到、也無法觸發。
